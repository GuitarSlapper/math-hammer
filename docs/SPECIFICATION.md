# ТЗ для Codex: MathHammer v2 — калькулятор урона и локальная история для Android

> Это **полная заменяющая версия** ТЗ. Не требуется применять предыдущий файл как патч. Дизайн: [DESIGN_GUIDE.md](DESIGN_GUIDE.md) и макеты `design-kit/references_v2/`.

## 1. Задача

Создай **работающее нативное Android-приложение** на **Kotlin + Jetpack Compose + Material 3**, которое вычисляет ожидаемый (средний) урон атак по одной однородной цели по базовой последовательности атак **Warhammer 40,000, 11-я редакция (2026)**.

Приложение предназначено для быстрых расчётов прямо за игровым столом. **Интернет, регистрация, база юнитов, API и сервер не нужны.** Сохранённые расчёты должны жить исключительно в локальной базе данных устройства. Интерфейс — **на русском**, обозначения характеристик оставь принятые в игре (`A`, `BS/WS`, `S`, `AP`, `D`, `T`, `Sv`, `Inv`).

Обязательно показывай **две разные метрики**:
1. **Средний урон за 1 атаку** — математическое ожидание урона от **одного атакующего кубика** с учётом попадания, ранения и проваленного сейва.
2. **Средний суммарный урон** — математическое ожидание урона от **всех A атак**.

Важно: это **потенциальный урон после сейвов**, а не вероятность уничтожить юнит или фактически снятые Wounds с моделей.

## 2. Платформа и архитектура

- Android, Kotlin, Jetpack Compose, Material 3.
- Создай стандартный Android Gradle-проект, открываемый в Android Studio. `minSdk` 26 (или выше, если шаблон проекта требует); `targetSdk` — актуальный установленный SDK.
- Два основных экрана: «Калькулятор» и «История», а также диалог «Сохранить расчёт» и действия с сохранённой записью. Портретная ориентация удобна; при повороте/пересоздании экрана ввод не должен теряться.
- Разделение на `MainActivity`, навигацию/Compose-экраны, `DamageCalculator` (чистая Kotlin-логика), `ViewModel`, `Repository`, локальную БД Room, модели входа/результата и unit-тесты.
- **Вся математика отделена от UI.** Логика не зависит от Android/Compose и тестируется обычными JVM-тестами.
- Для хранения использовать только локальный Room (Jetpack/AndroidX; соответствующий компилятор KSP), корутины и Flow. Других сторонних SDK не нужно. Без рекламы, трекеров, разрешений и сетевых запросов.
- Оформи README с запуском проекта и инструкцией по расчёту.

## 3. Поля ввода

### Атакующий

| Поле | Значение | Диапазон для MVP | Пример |
|---|---|---|---|
| `A` | **Общее число атакующих кубиков**, уже суммированное по всем одинаковым атакам | целое 0–9999 | `12` |
| `BS/WS` | Необходимое значение D6 для попадания | 2+ … 6+ | `3+` |
| `S` | Strength | целое 1–999 | `8` |
| `AP` | Armor Penetration со знаком, **0 или отрицательное число** | целое −99 … 0 | `−2` |
| `D` | Фиксированный Damage одной неотсейвленной атаки | целое 1–999 | `2` |

### Защитник

| Поле | Значение | Диапазон для MVP | Пример |
|---|---|---|---|
| `T` | Toughness | целое 1–999 | `5` |
| `Sv` | Обычный Save | 2+ … 6+ | `3+` |
| `Inv` | Invulnerable Save | `Нет` или 2+ … 6+ | `4+` |

**Итого 8 полей**: пять у атакующего и три у защитника. Wounds, количество моделей и вероятность уничтожения **не нужны**.

Рекомендуемые элементы: числовые текстовые поля для `A`, `S`, `AP`, `D`, `T`; выпадающие списки/сегментированные селекторы для `BS/WS`, `Sv`, `Inv`. Для `AP` обязательно поддерживать ввод минуса. Используй понятные подписи, не полагайся на одни аббревиатуры.

Значения при первом открытии: `A=12`, `BS/WS=3+`, `S=8`, `AP=-2`, `D=2`, `T=5`, `Sv=3+`, `Inv=4+` — демонстрационный пример.

## 4. Математическая модель

Обозначения:

- `pHit` — вероятность успешного попадания одной атаки;
- `pWound` — вероятность ранения **при условии попадания**;
- `pFailSave` — вероятность провала сейва **при условии ранения**;
- `D` — фиксированный урон после проваленного сейва;
- `A` — число одинаковых атак.

**Основные формулы:**

```text
pSuccessfulAttack = pHit × pWound × pFailSave
averageDamagePerAttack = pSuccessfulAttack × D
averageTotalDamage = A × averageDamagePerAttack
expectedUnsavedAttacks = A × pSuccessfulAttack
```

Все значения вероятностей храни как `Double` от 0 до 1. **Никогда не округляй промежуточные величины.** Округление — только для отображения в интерфейсе.

### Шаг 1. Попадание

Для `BS/WS = hitTarget`, где `hitTarget ∈ {2,3,4,5,6}`:

```text
pHit = (7 - hitTarget) / 6.0
```

Пример: 3+ означает `4/6 = 0.666666...`. Натуральная 1 всегда провал, натуральная 6 всегда попадание; для диапазона 2+…6+ формула это учитывает.

### Шаг 2. Ранение: сравнение S и T

Определи порог `woundTarget` **строго в этом порядке**:

```text
if S >= 2 × T         -> 2+
else if S > T         -> 3+
else if S == T        -> 4+
else if 2 × S > T     -> 5+
else                  -> 6+
```

Затем:

```text
pWound = (7 - woundTarget) / 6.0
```

Используй `Long` для умножения `2 * S`/`2 * T`, чтобы не допускать переполнений при изменении диапазонов в будущем.

Пограничные случаи: `S=8, T=4 -> 2+`; `S=4, T=8 -> 6+`; `S=5, T=8 -> 5+`; `S=T -> 4+`.

### Шаг 3. Обычный Save, AP и Invulnerable Save

`AP` пользователь вводит **со знаком**, например `-2`. Поэтому порог обычного сейва:

```text
armorSaveTarget = Sv - AP
```

Пример `Sv=3+`, `AP=-2`: требуется 5+ (`3 - (-2) = 5`).

При наличии инвуля он не меняется из-за AP. Для **однородной** цели вероятность провала определяется более выгодным для защитника порогом:

```text
effectiveSaveTarget =
    if Inv присутствует: min(armorSaveTarget, Inv)
    else: armorSaveTarget

pFailSave = clamp((effectiveSaveTarget - 1) / 6.0, 1.0/6.0, 1.0)
```

`clamp(x, min, max) = max(min, min(x, max))`.

- Нижняя граница `1/6` соответствует правилу: немодифицированная 1 на сейве всегда проваливается.
- Верхняя граница `1.0`: при требовании 7+ и хуже обычный сейв на D6 недостижим, если нет более выгодного инвуля.
- **Не выполняй два сейва последовательно и не перемножай шансы провала Sv и Inv.** Это один сейв, который проверяется с учётом правил обычного сейва и инвуля.

Примеры:

```text
Sv=3+, AP=-2, Inv=4+ -> armor=5+, effective=4+, pFailSave=3/6
Sv=3+, AP=-2, Inv=Нет -> armor=5+, effective=5+, pFailSave=4/6
Sv=2+, AP=0, Inv=5+ -> effective=2+, pFailSave=1/6
Sv=3+, AP=-5, Inv=Нет -> effective=8+, pFailSave=6/6
```

### Шаг 4. Средний урон

```text
averageDamagePerAttack = pHit × pWound × pFailSave × D
averageTotalDamage = A × averageDamagePerAttack
```

**«1 атака» = один атакующий кубик, а не один боец, не один выстрел с несколькими атаками и не одна уже попавшая атака.** Это определение зафиксировать в подсказке UI.

Если `A=0`, суммарный урон равен `0`, но значение урона **за одну гипотетическую атаку** всё равно вычисляется по остальным параметрам.

## 5. Контрольный пример (должен совпасть в приложении)

```text
Атакующий: A=12, BS/WS=3+, S=8, AP=-2, D=2
Защитник:  T=5, Sv=3+, Inv=4+

pHit = 4/6 = 0.6666666667
woundTarget = 3+ (поскольку T < S < 2T)
pWound = 4/6 = 0.6666666667
armorSaveTarget = 3 - (-2) = 5+
effectiveSaveTarget = min(5, 4) = 4+
pFailSave = 3/6 = 0.5

pSuccessfulAttack = (4/6) × (4/6) × (3/6) = 2/9
averageDamagePerAttack = (2/9) × 2 = 4/9 = 0.4444444444
averageTotalDamage = 12 × (4/9) = 16/3 = 5.3333333333
expectedUnsavedAttacks = 12 × (2/9) = 8/3 = 2.6666666667
```

В интерфейсе (русская локаль):

```text
Средний урон за 1 атаку: 0,444
Средний урон за 12 атак: 5,33
```

Дополнительно в небольшом сворачиваемом блоке «Детали расчёта» можно показать: `Попадание 66,7%`, `Ранение 66,7%`, `Провал сейва 50,0%`, `Среднее число атак, прошедших сейв: 2,67`. **Этот блок второстепенен**: два значения урона должны визуально доминировать.

## 6. UX/UI

- Главный экран «Калькулятор»: заголовок «MathHammer», карточки «Атакующий» и «Защитник», заметный блок «Результат», кнопка «Сохранить» и переход «История».
- Большой результат: **Средний суммарный урон**; рядом или ниже: **Средний урон за 1 атаку**. Обе метрики видны без дополнительных действий.
- Результат пересчитывается **сразу при каждом валидном изменении** поля, без кнопки «Рассчитать».
- Поля удобно редактировать одной рукой; интерфейс адаптирован к экрану телефона и экранной клавиатуре (прокрутка, отсутствие перекрытия результатов, нормальные hit targets).
- Форматируй числа по русской локали (`5,33`; `0,444`), итоги: 2 знака, результат за атаку: 3 знака. Избегай научной нотации.
- Когда поле очищено во время редактирования или введено недопустимое значение, покажи ошибку именно рядом с этим полем. Вместо ложного `0`/`NaN` отображай в результатах `—` и объяснение «Проверьте значения».
- Сохраняй редактируемый черновик при повороте экрана/восстановлении Activity (`SavedStateHandle`/`rememberSaveable`). История сохраняется между запусками в Room; черновик не обязан сохраняться между холодными запусками, если явно не выбран из истории.
- Короткое постоянное пояснение: «Ожидаемый урон после сейвов; не учитывает избыточный урон и количество Wounds цели».
- Желательно поддержать тёмную тему ОС. Не использовать чужие логотипы и изображения Warhammer.

## 7. Валидация

- `A`: целое 0–9999.
- `BS/WS`, `Sv`, `Inv`: только перечисленные пороги; `Inv` может отсутствовать.
- `S`, `T`, `D`: строго положительные целые (до 999).
- `AP`: целое от −99 до 0; положительный AP не допускается.
- Удалённые/пустые значения во время редактирования не превращать молча в 0.
- Не допускать крашей при вводе `-`, пробелов, слишком длинных строк, недопустимых символов.
- В расчёт допускать только валидный объект входных данных; при ошибке возвращать явный результат валидации, а не подставлять фиктивные значения.

## 8. Чистая модель расчёта (рекомендуемый API)

```kotlin
data class DamageInput(
    val attacks: Int,
    val hitTarget: Int,
    val strength: Int,
    val armorPenetration: Int, // 0 или отрицательное число
    val damage: Int,
    val toughness: Int,
    val saveTarget: Int,
    val invulnerableSaveTarget: Int? // null = нет инвуля
)

data class DamageResult(
    val woundTarget: Int,
    val effectiveSaveTarget: Int,
    val hitProbability: Double,
    val woundProbability: Double,
    val failedSaveProbability: Double,
    val successfulAttackProbability: Double,
    val expectedUnsavedAttacks: Double,
    val averageDamagePerAttack: Double,
    val averageTotalDamage: Double
)

// Валидирует вход; на ошибке возвращает явную ошибку/exception
fun calculateDamage(input: DamageInput): DamageResult
```

Допустимо использовать `sealed interface CalculationState` для UI, отделяя `Valid(result)` от `Invalid(errors)`. Не смешивай форматирование чисел с функцией расчёта.

## 9. Обязательные unit-тесты

Создай тесты чистой Kotlin-логики (JVM, JUnit) с допуском для `Double` `1e-9`:

1. **Контрольный пример**: `A=12, hit=3, S=8, AP=-2, D=2, T=5, Sv=3, Inv=4` ⇒ `perAttack=4/9`, `total=16/3`.
2. **Линейность по A**: при прочих равных `averageDamagePerAttack` одинаков для `A=1` и `A=100`, а `averageTotalDamage` меняется ровно в 100 раз.
3. **A=0**: `averageTotalDamage=0`, а `averageDamagePerAttack` остаётся положительным для исходного примера.
4. **Границы Wound**: `S/T=8/4 -> 2+`, `6/5 -> 3+`, `5/5 -> 4+`, `5/8 -> 5+`, `4/8 -> 6+`.
5. **Выбор сейва**: `Sv=3, AP=-2, Inv=4` ⇒ `effective=4`, `pFail=0.5`.
6. **Без инвуля**: `Sv=3, AP=-2, Inv=null` ⇒ `effective=5`, `pFail=4/6`.
7. **Броня лучше инвуля**: `Sv=2, AP=0, Inv=5` ⇒ `effective=2`, `pFail=1/6`.
8. **Броня полностью пробита**: `Sv=3, AP=-5, Inv=null` ⇒ `pFail=1.0`.
9. **Ошибки**: `hit=1`, `T=0`, `AP=+2`, `D=0`, `Inv=7`, `A<0` корректно отклоняются.
10. **Нет преждевременного округления**: расчёт контрольного примера даёт `5.333333...`, а не `5.28` или `5.34` из округлённых шагов.

## 10. Что НЕ делать в MVP

- Не считать вероятность уничтожения отряда и не симулировать кубики.
- Не добавлять `Wounds`, число моделей, модель распределения урона или ограничение здоровья цели.
- Не реализовывать рероллы, модификаторы бросков, Cover, Feel No Pain, Lethal Hits, Sustained Hits, Devastating Wounds, Mortal Wounds и особые способности.
- Не поддерживать `D3`/`D6` для A и D в первой версии: только фиксированные целые значения. Возможное будущее расширение — математическое ожидание случайных характеристик.
- Не добавлять учёт разных групп моделей/разных защитных характеристик в одной цели.
- Не подключать базы данных игровых юнитов, API и сетевые сервисы. **Локальная Room-база сохранённых расчётов обязательна** и не является базой юнитов.

Это **сознательно упрощённая математическая модель** для одинаковых независимых атак по одной цели с одинаковыми `T`, `Sv`, `Inv`. Покажи это пользователю без впечатления, что приложение рассчитывает реальные уничтоженные модели.

## 11. Критерии приёмки

- Проект компилируется и запускается в Android Studio без ручного дописывания кода (если среда Codex позволяет — собери проект и прогони тесты).
- В калькуляторе ровно восемь основных полей ввода, две главные метрики и необязательные детали. Дополнительно есть экран истории и ввод имени сохранённого расчёта.

## 13. Новая функциональность: локальные сохранённые расчёты

### 13.1. Что считать «последними»

- **Сохраняются только записи по явному нажатию кнопки «Сохранить».** Автоматически не записывать каждый пересчёт, каждый ввод символа или каждый переход.
- Раздел называется «История» / «Сохранённые расчёты» и показывает **все явно сохранённые записи**, отсортированные по `updatedAt` от новых к старым. Нет искусственного лимита в 10/20 записей и автоматического удаления старых.
- Имена свободные: латиница, кириллица, пробелы и игровые термины. Пример: `Accursed Weapon vs Interceptors` (только пользовательская подпись, никакой загрузки характеристик по имени).
- Незаписанные изменения черновика НЕ перезаписывают сохранённую запись автоматически.

### 13.2. Сценарий «Новый расчёт → Сохранить»

1. Пользователь выставляет 8 параметров, приложение сразу выводит `averageDamagePerAttack` и `averageTotalDamage`.
2. Кнопка **«Сохранить»** активна только при валидном `DamageInput`.
3. Открывается `AlertDialog`/`ModalBottomSheet` с заголовком «Сохранить расчёт», полем **«Название»** и кнопками «Отмена»/«Сохранить».
4. Название обязательно: после `trim()` длина **1–80 символов** (Unicode code points), пустые строки/строки из пробелов запрещены. Кнопка подтверждения при ошибке недоступна, сообщение рядом с полем.
5. Результат сохраняется атомарно в SQLite вместе с 8 исходными характеристиками, обеими метриками и временем создания/изменения.
6. После успешного сохранения закрыть диалог, показать Snackbar «Расчёт сохранён». При ошибке записи показать понятное сообщение, не терять ввод и не закрывать диалог.
7. Повторное сохранение нового черновика с тем же именем **разрешено**: имена не уникальны, каждая операция «Сохранить как новый» создаёт собственную запись.

### 13.3. Сценарий «История»

- Открывается по кнопке нижней навигации/верхней панели «История». Текущий черновик калькулятора при переходе туда и обратно не теряется.
- Каждая строка показывает **название, локальные дату/время, краткие параметры** (`A12 · 3+ · S8 · AP−2 · D2` и `T5 · 3+ · Inv4+`) и **оба результата** (`0,444 / атака`, `5,33 всего`). На маленьком экране разрешён перенос строк без обрезки основных чисел.
- Сортировка: `updatedAt DESC, id DESC`; время хранить в UTC миллисекундах, форматировать по текущей локали и часовому поясу устройства.
- Касание карточки **открывает сохранённый расчёт в калькуляторе**, заполняет все 8 полей и пересчитывает показатели. Запись привязывается к редактируемому экземпляру (`editingSavedId`).
- Для привязанной записи доступны **«Сохранить изменения»** (обновляет ту же запись), **«Сохранить как новый»** (создаёт отдельную запись) и **«Отменить изменения»** (восстановить параметры из записи). Никакого неявного автосохранения изменений.
- Действия из меню `⋮` каждой строки: **«Переименовать»**, **«Удалить»**. Переименование меняет только название и `updatedAt`, входные характеристики и сохранённый результат не меняются.
- Удаление только по явному действию, со Snackbar «Расчёт удалён» и **«Отменить»** на короткое время либо с диалогом подтверждения (выбери один вариант; предпочтительно Snackbar с Undo). При отмене восстановить запись с исходным `id` и всеми полями.
- Пустое состояние: иконка, «Сохранённых расчётов пока нет», подпись «Сделайте расчёт и нажмите “Сохранить”», кнопка **«Новый расчёт»**.
- Нет регистрации, импорта, экспорта, сортировок по боевым фракциям, синхронизации, группировки или поиска в MVP. Не добавлять «Избранное» и заметки, даже если они встречаются в концептуальном moodboard.

### 13.4. Черновики и навигация

- «Новый расчёт» сбрасывает `editingSavedId` и открывает калькулятор с демонстрационными значениями (или с дефолтами, зафиксированными в разделе 3). Старый сохранённый расчёт при этом не удаляется.
- Если пользователь открыл запись из истории и поменял значения, показать рядом с заголовком ненавязчивую метку «Есть несохранённые изменения».
- При возвращении в историю **не надо автоматически сохранять** изменения. При действиях, которые уничтожат изменённый черновик (например, «Новый расчёт»/открытие другой записи), спросить «Сбросить несохранённые изменения?».
- При сохранении существующей записи обновить также оба математических результата из текущих валидных характеристик. Не сохранять устаревшие числа из UI.
- При открытии истории после перезапуска приложения данные должны быть доступны без интернет-соединения.

## 14. Модель данных и локальная БД

Использовать **Room + SQLite**, данные хранятся в `context.filesDir`/приватной песочнице приложения (Room создаёт БД в приватной директории `databases/`). Не использовать облачные БД, Firestore, Firebase, API, аккаунты или `SharedPreferences` для всей коллекции записей.

Рекомендуемая сущность Room (имена Kotlin-полей адаптируй к Room API выбранной версии):

```kotlin
@Entity(tableName = "saved_calculations", indices = [Index("updatedAtEpochMs")])
data class SavedCalculationEntity(
    @PrimaryKey(autoGenerate = true) val id: Long = 0,
    val title: String,
    val attacks: Int,
    val hitTarget: Int,
    val strength: Int,
    val armorPenetration: Int,
    val damage: Int,
    val toughness: Int,
    val saveTarget: Int,
    val invulnerableSaveTarget: Int?, // null = нет инвуля
    val averageDamagePerAttack: Double,
    val averageTotalDamage: Double,
    val calculationVersion: Int = 1,
    val createdAtEpochMs: Long,
    val updatedAtEpochMs: Long
)
```

**Почему сохраняем и входы, и результаты:** входные параметры позволяют снова редактировать/считать; snapshot значений сохраняет вывод, который пользователь видел в момент записи. При открытии всегда пересчитывай по актуальному `DamageCalculator` и используй его как источник истины для текущего UI; при изменении формул в будущем показывай предупреждение о несовпадении версий и обновляй snapshot только по явному сохранению.

**DAO/repository (минимум):**

```kotlin
@Dao
interface SavedCalculationDao {
    @Query("SELECT * FROM saved_calculations ORDER BY updatedAtEpochMs DESC, id DESC")
    fun observeAll(): Flow<List<SavedCalculationEntity>>

    @Query("SELECT * FROM saved_calculations WHERE id = :id LIMIT 1")
    suspend fun findById(id: Long): SavedCalculationEntity?

    @Insert
    suspend fun insert(value: SavedCalculationEntity): Long

    @Update
    suspend fun update(value: SavedCalculationEntity)

    @Delete
    suspend fun delete(value: SavedCalculationEntity)
}
```

Добавь в репозиторий операции `saveNew(title, input)`, `saveChanges(id, input)`, `rename(id, title)`, `delete(id)` и `restoreDeleted(entity)` либо транзакционную Undo-логику. Repository **самостоятельно валидирует** `DamageInput` и считает `DamageResult`: UI не имеет права передавать подделанные готовые метрики. Запись/переименование/удаление выполнять в `Dispatchers.IO`/suspend, не блокируя главный поток. Для `saveChanges` и `rename` проверять, что ID существует: не превращать ошибку в создание новой записи.

Используй `Long` UTC timestamp и/или инъекцию `Clock`, чтобы тестировать порядок сортировки и время без `Thread.sleep`. При миграциях Room **не использовать `fallbackToDestructiveMigration`**, чтобы не уничтожать историю. Напиши миграции для будущих изменений схемы.

## 15. Полная офлайн-работа и приватность

- Не добавлять `android.permission.INTERNET` и `android.permission.ACCESS_NETWORK_STATE` в `AndroidManifest.xml`; проверить итоговый merged manifest и зависимости.
- Не использовать analytics/crash-reporting/ad SDK, удалённые шрифты, изображения, WebView, HTTP-клиенты, Firebase, Play-services-синхронизацию.
- Шрифт **Exo 2** должен быть встроен в APK локальными ресурсами. Файлы шрифта скачиваются разработчиком по ссылке в DESIGN_GUIDE, включаются в проект вместе с лицензией OFL; не подключать через загрузку из интернета на устройстве.
- База хранится в приватной директории приложения. Удаление приложения обычно удаляет её вместе со всеми расчётами — предупредить об этом в README, при желании в справке.
- Для строгого требования «только на данном устройстве» запретить Android Auto Backup / cloud backup: `android:allowBackup="false"`; для актуальных Android дополнительно настроить `android:dataExtractionRules` и исключить данные БД из cloud-backup **и переноса на другое устройство**, а для старых — `android:fullBackupContent`/rules. Проверить поведение по документации/на целевых версиях ОС: одного `allowBackup=false` недостаточно, чтобы гарантировать отсутствие D2D-переноса на всех Android 12+ устройствах.
- Записи доступны в авиарежиме; сохранение/редактирование/удаление не зависит от подключения.
- Для MVP не нужно запрашивать разрешение на доступ к файлам, галерее или контактам.

## 17. Тесты новой функциональности

Добавить к тестам раздела 9 следующие тесты (unit/Room instrumentation, по доступности среды):

1. `saveNew` валидного черновика создаёт одну запись со **всеми восемью входными параметрами** и обоими точными результатами (`4/9`, `16/3`).
2. После закрытия и повторного открытия БД записи сохраняются, `observeAll()` отдаёт их без интернета.
3. Две записи с одинаковым названием сосуществуют как разные `id`.
4. Пустое/пробельное имя и имена более 80 Unicode code points отклоняются; корректные кириллические и латинские строки принимаются.
5. Список отсортирован по `updatedAt DESC, id DESC`; переименование меняет `updatedAt` и порядок, но не расчёт.
6. Открытие записи восстанавливает все 8 полей, а значение за атаку не зависит от `A`.
7. «Сохранить изменения» изменяет **ту же** запись и обновляет оба результата, не создаёт дубль; «Сохранить как новый» создаёт новую запись.
8. Изменение черновика без сохранения **не меняет данные** в истории, даже после перехода между вкладками.
9. Удаление убирает запись; Undo возвращает все данные и исходный `id`.
10. Ошибка БД не приводит к ложному Snackbar «Сохранено» и не закрывает диалог с потерей введённого имени.
11. UI-тесты: пустая история, сохранение, переименование, восстановление, подтверждение потери черновика; проверка screen rotation.
12. Проверка без интернета: запустить в авиарежиме и пройти весь цикл. Проверка merged manifest: `INTERNET` и `ACCESS_NETWORK_STATE` отсутствуют.

## 18. Критерии приёмки v2 и приоритеты

- Все критерии из раздела 11 остаются обязательными.
- Два экрана: **Калькулятор / История**, устойчивое состояние черновика.
- Кнопка «Сохранить» открывает диалог с обязательным названием; запись появляется в истории и переживает перезапуск приложения.
- История отображает названия, время, параметры и **два** результата; поддерживает открытие, переименование, явное обновление и удаление с Undo/подтверждением.
- Отсутствуют сетевые разрешения, SDK отправки данных, облачные резервные копии и синхронизация.
- Калькулятор продолжает корректно показывать **0,444 на атаку и 5,33 всего** на тестовом примере.
- Сначала реализовать/протестировать чистую математику, затем Room + Repository, затем UI/навигацию и тесты взаимодействий.
- Не писать «готово» без фактической сборки и тестов; если среда не позволяет — перечислить непроверенные этапы.
